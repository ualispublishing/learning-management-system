# AI provider adapters and prepared demo

The app keeps its existing `AIService` contract and review/publication flow. The new **server-only** `src/lib/ai/providerAdapter.server.ts` adds the vendor boundary: an `AIProvider` receives the authoritative prompt, schema, task, canonical extracted text with locations, requested count, locale and abort signal, and returns task JSON. `runAIProvider` checks source evidence and output before adding gateway-controlled provenance.

`createHttpJsonAIProvider` supports HTTPS JSON APIs with institution-defined request encoding, response decoding and secret-backed headers. Implement `AIProvider` directly for SDKs, streaming APIs or asynchronous jobs. This is an extensible interface; a different API still needs its own small mapping and integration tests. No API can be assumed wire-compatible, and no named external provider has been exercised with real credentials in this change.

## Current OpenAI integration status

On October 11, 2026, `createOpenAIResponsesProvider` was added in
`src/lib/ai/openaiProvider.server.ts`. It implements the Responses API request,
strict structured-output schema adaptation and response decoding, using the
existing provider boundary. Model, reasoning effort and output-token budget are
server configuration. No new dependency or live provider switch was added to
the demo. Tests use synthetic API envelopes and injected transports; no real
credentials, paid generation or live-model quality evaluation have been used.

The connector supplies `store: false`, sends located extracted text as reference
data, rejects redirects, and rejects refusals, incomplete responses, unexpected
tool output and multiple answers. The institution must still confirm its model
supports the chosen schema, reasoning effort and token limit. `store: false`
does not itself establish a data-retention or residency agreement.

OpenAI's strict schema requires all object fields and forbids arbitrary object
keys. The adapter represents optional syllabus fields as nullable, and grading
weights as ordered `{category, weight}` entries. It restores omitted fields and
the LMS's grading map before the independent application checks. Duplicate,
numeric-only or unsafe category labels are rejected to preserve the indexed
evidence mapping. Null unknown fields and generated approvals still fail.
See the [structured-output guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)
and [Responses text-generation guide](https://developers.openai.com/api/docs/guides/text).

OpenAI documents `gpt-6-astra` as an API model, including structured outputs.
Its model page lists text/image input, with audio/video unsupported as direct
modalities; those files need appropriate transcription/extraction before this
adapter's text-based workflow. See the
[official model documentation](https://developers.openai.com/api/docs/models/gpt-6-astra).

The active prepared pack was generated by an isolated Codex agent configured
with `gpt-6-astra` and `xhigh`, without inherited chat history. Its generation
record and explicit task-input snapshot are in
`demo/ai/generation/2026-10-06-isolated/`. The unchanged candidate outputs were
activated on October 7. An auditable same-day syllabus enrichment then added
five field groups by copying exact source passages; see
[the revision record](../demo/ai/generation/2026-10-07-course-mapping/README.md).
The active extraction schema is `syllabus.v1.5.0`; the original agent input
snapshot remains unchanged. This establishes configured-agent attribution, not a
standalone API generation receipt or identical API context. The prior pack with
unrecorded model attribution is archived separately. OpenAI describes generation
as nondeterministic and recommends
evaluations and model-version pinning in its
[prompt engineering guide](https://developers.openai.com/api/docs/guides/prompt-engineering).

For live API acceptance, generate and archive outputs through the exact
production prompt, extraction and provider path; record the returned model,
reasoning settings, request/response IDs, source/extraction/prompt hashes and
any edits. Evaluate repeated fresh runs against instructor-approved criteria.
Only replaying the archived response guarantees the same saved content.

The actual course review and saved-content views now show generation attribution.
For prepared results, the demo server adds `provenance.preparedGeneration` only
after checking the generation-record hash and its source/extraction/result hashes.
The bounded record carries the authoring tool/date/model, optional reasoning,
context and enrichment note, and record SHA-256. Client validation requires the
prepared replay model and a document digest; every card must agree. Publication
retains it in syllabus metadata or the study set's `metadata.ai.provenance`.
Old records without authoring metadata remain explicitly unattributed. Live
results display the service-reported model/adapter label, because an adapter ID
can be the fallback when no API model receipt was supplied. No view substitutes
the current configured model for the model that produced saved content.

## OpenAI server integration

This is a server integration example for an authenticated, authorized gateway,
after file validation and extraction. Configuration and secret/audit services
are supplied by the deploying institution; they are not browser inputs.

```ts
import { createOpenAIResponsesProvider } from '../src/lib/ai/openaiProvider.server';
import { runAIProvider } from '../src/lib/ai/providerAdapter.server';

const provider = createOpenAIResponsesProvider({
  model: serverConfig.model,
  reasoningEffort: serverConfig.reasoningEffort,
  maxOutputTokens: serverConfig.maxOutputTokens,
  getApiKey: signal => secrets.read('openai-api-key', { signal }),
});

const result = await runAIProvider(provider, task, input, extractedSource, requestId, {
  signal: clientDisconnectSignal,
  timeoutMs: 120_000,
  onReceipt: receipt => auditStore.saveGenerationReceipt(receipt),
});
// Return the validated draft for the existing instructor review flow.
```

Receipts include the API-reported model, response ID, HTTP request ID, configured
reasoning effort, token counts when supplied, gateway request ID, prompt version,
exact encoded-request SHA-256, source/document digests and validated-output hash.
The request digest covers the effective instructions, wire schema, source,
model and generation options, but excludes the credential header. The receipt
contains no source text, API key or reasoning content. The result's existing
`provenance.model` now uses the API-reported model when available. Other provider
implementations retain their configured ID unless they report trusted metadata.
Metadata is request-scoped, so concurrent results cannot swap attribution.
The gateway snapshots input/source drafts before asynchronous work, and the
transport hashes the actual sent body rather than reconstructing it later.

The gateway calls `onReceipt` only after validation. A configured receipt-store
failure prevents returning the result. The optional [reference AI gateway](../server/ai-contract.md)
now uses this hook to commit receipts with validated results in SQLite. Custom
gateways must supply their own storage. Archive the exact extracted source, request
configuration and output under institution access controls for reproducibility;
hashes alone cannot reconstruct them.

Every provider run now accepts caller cancellation and a cleared-on-completion
deadline (120 seconds by default, at most 600 seconds). Credential lookup,
fetching and response reading are bounded; cancellation during credential lookup
prevents a late request, and stalled response streams are cancelled and unlocked.
The caller stops awaiting an SDK that ignores its signal, but the SDK must still
honour that signal to stop its own underlying work. No automatic retry or model
fallback is performed, so a failure does not silently initiate another paid run.
Source text is limited to 500,000 characters, located segments to 10,000 and
1,000,000 total characters, encoded requests to 8 MB and responses to 2 MB.

Verification on October 11: 15 connector/boundary tests cover schema translation,
input snapshots, exact request hashes, concurrent attribution, unsupported
outputs, cancellation, stalled streams, size limits and redacted failures.
`npm run check` passed all 485 app tests and 270 synthetic journeys; the production
web export and exported-file verification passed. Existing real loopback tests
still exercise all six prepared formats and syllabus/lesson publication through
the shared demo backend. These checks are not live OpenAI acceptance or a model
accuracy measurement. See the [verification record](../demo/ai/verification/README.md).

## Example server integration

This illustrative API shape belongs to a hypothetical institution gateway; adapt the mapping to the selected provider's current documentation:

```ts
import { createHttpJsonAIProvider, runAIProvider } from '../src/lib/ai/providerAdapter.server';

const provider = createHttpJsonAIProvider({
  id: 'institution-model/revision-1',
  endpoint: serverConfig.modelEndpoint,
  headers: async () => ({ authorization: `Bearer ${await secrets.read('model-api-key')}` }),
  encode: request => ({
    instruction: request.systemPrompt,
    schema: request.responseSchema,
    input: request.source,
    task: request.task,
    locale: request.locale,
    maxCards: request.requestedCardCount,
  }),
  decode: raw => (raw as { result: unknown }).result,
});

// After server authentication, course authorization, upload validation and extraction:
const response = await runAIProvider(provider, task, input, {
  text: extracted.canonicalText,
  segments: extracted.segments, // exact text + page/slide/heading/timestamp
  documentSha256: uploadedFileSha256,
}, requestId);
```

Use the selected institution's authenticated gateway at `/lms/v1/ai/generate` with the multipart contract in `institution-integration.md`; the application uses `InstitutionAIService` or an injected institution `AIService`. The development URL setting `EXPO_PUBLIC_LMS_AI_BASE_URL` points to that gateway, never to a vendor endpoint containing credentials; production must inject the authenticated service during bootstrap. Adapter headers and provider selection belong on the server, not in user-supplied request fields. HTTPS is required except explicitly enabled loopback testing. Redirects are rejected and JSON responses are limited to 2 MB.

## Client authentication and course scope

`InstitutionAIService` supports bearer tokens and explicit same-origin cookie
authentication. These are client-to-institution credentials; the separate vendor
API key remains on the institution's server. Bearer mode is the default and uses
`credentials: 'omit'`, so it cannot also send browser cookies. For a web gateway
behind the exact HTTPS application origin:

```ts
const aiService = new InstitutionAIService({
  baseUrl: window.location.origin,
  authentication: 'same-origin-cookie',
  sourceProfile: 'text-v1', // Matches the reference gateway's text/caption extractor.
  requestRecovery: 'history-v1', // Only for a gateway implementing this contract.
});
// Supply during production bootstrap once all required institution services exist.
const draft = await aiService.extractSyllabus({
  courseId: course.id,
  courseTitle: course.title,
  document: selectedDocument,
});
```

Cookie mode rejects a different origin, port or base path, non-HTTPS URLs,
native/server callers without a browser origin, and any token callback. It
rechecks the origin on each request and uses browser-managed HttpOnly cookies;
JavaScript does not read a cookie or manually set Cookie/Origin headers. The
gateway must enforce the current session and exact Origin/CSRF policy itself.
Cookie mode retains remote provenance checks even on HTTPS localhost. A 401 or
403 stays visible and never falls back to bearer, prepared mode or another API.

Every remote request now requires a stable `courseId`, at most 128 characters,
matching the institution gateway identifier contract. The actual course syllabus
and flashcard flows supply it. The local prepared showcase can continue without
a course because it neither creates nor rewrites one. Course title is context
only; neither it nor a client-supplied ID authorizes access. Before processing or
charging, a live gateway must verify course existence, installation and the
current principal's permission for the requested task. It must recheck access
before retaining or returning output, and bind its audit/idempotency records to
that principal, installation, course and effective input.

The HTTP client snapshots its configuration and input/document metadata before
credential lookup, preventing a mutable draft from changing course or source
mid-request. Changing course in the flashcard review resets consent and pending
review state, even when titles and material match; late results for the previous
course are ignored. This does not cancel work already accepted by a remote
provider. Server cancellation, session-revocation checks and cost accounting
remain gateway responsibilities.

The reference OIDC service now supplies an optional cookie-authenticated
`POST /lms/v1/ai/generate` and principal-scoped request-status route. It authorizes
course staff, stores inputs/results/receipts in SQLite, prevents duplicate
generation within retention, and bounds concurrent work and daily reservations.
See the [implemented profile](../server/ai-contract.md) for private configuration,
supported formats, quotas, expiry and uncertain-outcome handling. Full app SSO,
authorized asset publication, original-source retrieval
and live provider acceptance remain work. Custom `AIService` implementations
still need equivalent authorization and transport behavior. Tests use synthetic
provider responses without production credentials or paid requests.

The gateway can attach `provenance.sourceReviewNotices` from its trusted extractor:
at most 10 nonblank strings of 600 characters. The provider boundary snapshots
them before generation and includes them in the output receipt hash. They are
not model-generated warnings or permission to publish. The actual flashcard and
syllabus review views show them as literal text, and publication metadata retains
them. Cross-card provenance must agree, including notes, request ID and model.
A declared `X-LMS-AI-Review-Notices: present` header without inline notes is an
error; older saved results may need operator inspection instead of a fresh run.

With `requestRecovery: 'status-v1'`, a submitted failure exposes an `AIRequestError`
containing its request ID and a read-only saved-result check. The real course
review flows offer **Check saved result** separately from **Start a new generation**.
Checks use refreshed credentials and the original course/task/source snapshot,
validate status and output, and never issue another generation POST. Processing,
uncertain, expired, missing and forbidden requests remain explicit outcomes.
Recovered output is unverified until instructor review. A 30-second check deadline
also covers stalled credentials/transports/readers; late response bodies are
cancelled. Unknown services do not receive speculative status requests.

`history-v1` additionally supports recovery after reload. Both editors offer
**Find saved AI requests** after the original source is reselected and processing
rights are confirmed. History is principal/course/task scoped, limited to 20
summaries per page, and excludes source bodies and results. The recovery action
uploads the reselected source to a dedicated `/requests/{requestId}/recover`
endpoint, which verifies the original source and settings and can never start a
provider call. Expired/missing requests stay unavailable rather than generating
again. The saved count/language are shown to help match settings; source bytes,
filename/MIME and the prompt version must also agree. Reviewer edits are not
recovered, and recovered drafts require fresh human verification.

Sources and credentials are not added to browser storage. Original-source
retrieval and billing reconciliation remain work. See the full
[history contract](../server/ai-contract.md#recovery-after-reload-history-v1).
The prepared local replay does not opt into these live recovery profiles.

## Source processing and review boundaries

The adapter receives **already extracted** source text. The prepared demo supplies saved extraction for six known files. `textExtraction.server.ts` now extracts arbitrary supported UTF-8 TXT, Markdown, WebVTT and SRT files into that same provider contract, including through the authenticated reference route. The route implements bounded upload/storage, cancellation, retained request keys, course authorization and reservation quotas for this narrow profile. It does not implement general PDF/DOCX/PowerPoint/RTF parsing, OCR or speech transcription. Those require isolated, bounded workers, supported-upload controls and operational monitoring appropriate to deployment.

### Text and caption extraction

Use `extractTextSource({bytes, name, mimeType, signal})` after authorization and
upload checks. It returns `{source, extraction}`: canonical text and located
passages ready for `runAIProvider`, plus extraction version, independent file,
text and passage hashes, counts, normalization records and review notices.
Persist the extraction record with the original bytes and generation receipt;
present its notices to the reviewer. The provider runner accepts `source` and
does not automatically persist or display the accompanying extraction record.

```ts
import { extractTextSource } from '../src/lib/ai/textExtraction.server';

const extracted = extractTextSource({
  bytes: validatedUpload.bytes,
  name: validatedUpload.name,
  mimeType: validatedUpload.mimeType,
  signal: clientDisconnectSignal,
});
await sourceStore.saveExtraction(extracted); // institution-supplied storage
const draft = await runAIProvider(provider, task, input, extracted.source, requestId, {
  signal: clientDisconnectSignal,
  onReceipt: receipt => auditStore.saveGenerationReceipt(receipt),
});
// Include extracted.extraction.warnings in the instructor's review response.
```

The local CLI needs no credentials and makes no model request:

```sh
npm run ai:extract -- --input demo/ai/sources/mit-6.0001-syllabus.txt --out /tmp/lms-syllabus-extracted.json
npm run ai:extract -- --input demo/ai/sources/mit-6.0001-lecture1-captions.vtt --out /tmp/lms-captions-extracted.json
```

Choose a new output path each time: existing files are never overwritten. Output
contains the full source text and uses owner-only file permissions on Unix.
`extractTextFile` is a local maintenance helper, not an HTTP path resolver;
never pass an untrusted request path to it. Neither this CLI nor the extractor
changes the demo pack or enables arbitrary live uploads in the UI.

- Text keeps Unicode, punctuation, Markdown and whitespace. BOM removal and
  line-ending normalization are recorded. Paragraphs use original line numbers;
  long single-line fragments overlap and report explicit UTF-16 column ranges.
- Captions retain payload wording and order, grouping adjacent cues into located
  passages with timestamps and source lines. Windows overlap by one cue when
  possible, preserving context across short adjacent captions. They are bounded
  to 6,000 characters and a 60-second span, except a single longer-duration cue.
  A quotation must still fit one returned passage to pass evidence validation.
- This is a conservative extraction profile, not a full subtitle renderer or
  conformance validator. Recognized WebVTT display settings and comment/layout
  blocks are excluded with notices; layout values are not semantically validated.
  Tags, entities, speaker markup and inline timestamps remain literal source
  text, with a review notice. Nothing is rendered, executed or decoded as HTML.
  Missing separators, malformed/out-of-order timing, duplicate identifiers,
  untimed blocks and timestamp maps fail instead of yielding partial output.
  Literal `-->` within caption payloads is also rejected by this strict profile.
  Only UTF-8 SRT is supported; other encodings need an explicit conversion.
- Limits are 2 MB of uploaded bytes, 500,000 decoded characters, 20,000 lines,
  10,000 cues/passages, 6,000 characters per passage and 1,000,000 total passage
  characters. Binary/encoding/MIME mismatches and oversize inputs are rejected.
  Cancellation is checked before/after synchronous parsing and between bounded
  local file reads; parsing itself is not an asynchronous worker service.

For a VTT/SRT file, `documentSha256` identifies the **caption file**, not its
associated audio/video. A future transcription workflow must separately retain
and verify the relationship to the media digest and any timestamp offset. These
checks establish source traceability, not transcript accuracy or answer quality.
Format references: [W3C WebVTT draft](https://www.w3.org/TR/webvtt1/) and
[Library of Congress SRT description](https://www.loc.gov/preservation/digital/formats/fdd/fdd000569.shtml).

Keep document hashing separate from canonical extracted-text hashing. Persist exact source bytes and both digests. Treat extracted text as reference data, including any embedded instructions. Validate source locations and quotations; reject unknown response fields, duplicates and excess cards. Provider-generated approval and provenance are rejected. Every card remains unverified until a human reviews it. Quotes being present in a source does not prove an answer is correct or complete.

For live processing, benchmark against institution-approved answer sets, test prompt injection and extraction failures, measure unsupported claims and missed information, and require instructor acceptance. Do not use a model's confidence score as a measured accuracy percentage.

## Prepared local mode

The separate `/ai-demo` showcase calls the same `InstitutionAIService` and `/lms/v1/ai/generate` endpoint as the course flow, explicitly pinned to the local prepared backend. It displays the output without invoking course/content repositories or storing review approval. The shared `mapSyllabusToCourse` helper keeps preview field destinations consistent with course imports. The source preview endpoint serves only the allowlisted pack's extracted text. Resetting or switching examples clears component state, and stale responses cannot replace the current example.

`npm run demo:multiuser` explicitly enables `EXPO_PUBLIC_LMS_PREPARED_AI_DEMO=1` in the development build and uses the loopback demo backend. `prepared-demo/v1` selects output by uploaded **SHA-256**, never filename. Unknown or edited sources, wrong task/kind/prompt version and unsupported locales fail visibly. It never falls back to an external provider. The shared demo backend validates the complete pack at startup.

The UI labels pre-generated results and shows source-check details. Material source files and video captions use opaque stored HTTPS references that the explicitly enabled local demo resolves to its loopback file server. Production HTTPS validation is unchanged. Prepared assets do not provide production storage, authentication or learner-data durability.

See `demo/ai/README.md` for source files, provenance, limits, human review steps and the MIT noncommercial licence restriction. Run `npm run demo:ai:check` for the reproducible pack check. `tests/prepared-ai.test.ts` exercises two distinct HTTP response shapes and real local multipart/replay/retention paths, including changed-file rejection, invalid evidence and reference drift.
