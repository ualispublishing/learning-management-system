## Correctness and security changes completed

- Replaced fabricated authentication behavior with an injectable institution SSO identity boundary. Demo identity switching is development-only.
- Production now fails closed when institution repositories or an authenticated AI adapter have not been configured; demo data and the unauthenticated environment-URL AI shortcut are development-only.
- Split institution-level roles from course memberships and applied one centralized course-role policy to content authoring, configuration, rosters, grade analytics, grading, groups, staff chat, and live hosting. A session-wide administrator claim does not silently become a course role; privileged course access requires an explicit course enrollment so chat and grading audit identities remain valid.
- Added a strict, atomic schema v1 validator for users, courses, enrollment references, first-class group sets, content, assessments, learner study cards, threads, messages, replies, attachments, submissions, grade audits, IDs, timestamps, IANA time zones, term ordering, HTTPS URLs, grading totals, field lengths, cardinality, and a 10 MB root payload ceiling. Institution content and assessment questions now require backend-stable IDs instead of order-derived fallbacks that could change when JSON is reordered.
- Added a backend-neutral snapshot/mutation repository adapter with HTTPS enforcement, bearer authentication, tenant/version headers, timeouts, request/response limits, idempotency keys, atomic batches, exact acknowledgement checks, revision conflict fields, and bounded cursor upserts that resolve references against their validated base snapshot. Fixed an ETag concurrency gap: HTTP snapshots now preserve/verify response ETags, writes send `If-Match`, successful acknowledgements must return and advance the ETag, custom adapters follow the same rule, and malformed/control-bearing/stale tokens or unknown acknowledgement fields fail closed. Acknowledged cursor/ETag advances are also written into the validated encrypted-cache snapshot, preventing restart from reverting to stale concurrency metadata. Response bodies are stopped while streaming at the configured byte ceiling rather than allocated fully and checked afterward.
- Added architecture/source descriptors with validated read/write/realtime capabilities, fail-closed pre-transport checks for unsupported mutations, optional directory email, and atomic cursor tombstones. The post-upsert effective snapshot is revalidated so provider deletes and roster add/drop cannot retain orphaned courses, content, conversations, messages, or submissions.
- Unified remote-service hardening: production institution, AI, and asset endpoints require HTTPS even when the hostname is localhost; successful remote responses require JSON content types; insecure source URIs and unknown/malformed asset response fields fail closed.
- Required principal-scoped snapshots and rejected over-broad courses, conversations, student submissions, answer keys, and unreleased grades before they enter client state. Message reads and cached-account switches are re-authorized, and optional offline caches are principal-keyed.
- Fixed `upsert` imports that silently replaced unrelated visible courses, content, and threads. Post-merge derived counts are recomputed, and development file imports now commit one coherent repository snapshot including submissions and tombstones rather than updating the screen while leaving attempt/live-session repositories stale. Client file imports are development-only; production ingestion belongs on the audited server endpoint.
- Removed default local persistence of institution PII/grades. Offline caching is opt-in through an encrypted, principal-keyed institution-supplied cache. Fresh network data always wins atomically; stale cached submissions can no longer override a successful server load. The app never mixes partial network and cache sources, visibly labels offline fallback, refreshes the cache only after validated loads/mutations, rejects over-broad cached data, and attempts cache erasure on logout.
- Replaced no-op course/content updates with repository-confirmed mutations that merge into the latest state and expose visible errors. Critical assessment, syllabus, grade, submission, and content-bundle saves now wait for acknowledgement before closing. Full read/validate/send/commit transactions and nested group edits are serialized locally to prevent same-client lost updates; server compare-and-swap remains mandatory for multi-client safety. Submission and grade revisions now advance exactly once, learner attempts become immutable after submission, restore sends an explicit JSON `null` clear, and the UI consumes the repository-sanitized attempt rather than client-computed grading fields.
- Made account initialization a single atomic commit and added generation guards at both repository and store layers. Overlapping logins, snapshot fetches, mutations, history loads, and realtime callbacks from a prior principal cannot repopulate the new account’s state.
- Added atomic creation for content bundles and external grade columns/submissions.

## Institution launch gates

These cannot be completed solely in this repository because they depend on the deploying institution:

1. Implement and contract-test the snapshot/mutation gateway against the target SIS/LMS/database schema, including ETag/revision compare-and-swap, idempotency replay, server timestamps, atomic attempt creation, and atomic grading transactions.
2. Configure real SSO, secure token storage/refresh/revocation, tenant isolation, and server-side RBAC/ABAC.
3. Implement authenticated chat WebSocket/SSE and `LiveSessionRepository` transports. The client and HTTP contract now support message pagination/search and revision-safe moderation mutations; the institution service must implement them with replay, ordering, reconnect, retention/legal hold, moderation workflows, rate limits, abuse controls, and authoritative server timestamps.
4. Implement object storage with malware scanning, DLP, safe-content disposition, encryption, retention, legal hold, quotas, and orphan cleanup.
5. Implement the AI service with approved models/vendors, data-residency and no-training terms, OCR/extraction, server-owned prompt allow-lists, source-digest attestations, structured-output validation, cost/rate limits, evaluation datasets, and human escalation.
6. Run tenant-isolation penetration testing, mobile secure-storage review, dependency/SBOM scanning, privacy threat modeling, accessibility testing with assistive technology, device/browser compatibility tests, load/soak tests, backup/restore drills, and observability/alert exercises.
7. Obtain institution sign-off for FERPA/PIPEDA/GDPR, records retention, accessibility, academic integrity, and grading policy.

The client-side controls above are defense in depth. The server must remain authoritative for attempt start/deadline/late status, grading, source extraction attestations, role and group membership, mutation concurrency, and every realtime sender/participant identity.

## Product gaps to prioritize

The current assessment tools cover common quizzes, text responses, file uploads, timed questions, scales, rubrics, group work, attempts, grading, feedback, and grade release. See [`assessment-coverage.md`](./assessment-coverage.md) for the implemented/authority matrix and institution acceptance suite. A full enterprise LMS may additionally require:

- question banks, pools, randomization, variants, and secure import/export (QTI);
- numeric/formula, matching, ordering, hotspot, oral/audio/video, and accessible math questions;
- accommodations and per-user time/attempt overrides;
- anonymous/double-blind/moderated grading and grade-change approval workflows;
- outcomes/competency mapping, standards mastery, item analysis, and psychometrics;
- plagiarism/originality integrations, proctoring policy, and academic-integrity case workflows;
- LTI 1.3/Advantage, OneRoster, SCORM/xAPI, Caliper, and grade passback;
- weighted gradebook rules, drops, extra credit, missing/incomplete/excused states, overrides, grading schemes, curves, file feedback, and final-grade export;
- delegated cross-listing, sections, waitlists, add/drop reconciliation, and term rollover;
- notification preferences/digests, moderation/reporting, content versioning/approval, localization, and audit exports.

Enrollment lifecycle is a specific schema milestone: the current v1 contract models active course membership and rejects records whose owners/grader/senders are no longer enrolled. A production add/drop implementation needs effective-dated `active`, `withdrawn`, and `completed` enrollment history so withdrawals do not orphan historical submissions, grades, or messages. Do not implement removal by simply deleting the user from `course.staff`.

Static custom HTML/CSS renders in the web sandbox; native exposes its readable text as an accessible fallback but does not reproduce arbitrary authored CSS. An audited WebView/sanitizer integration is still needed before claiming visual cross-platform parity. Custom-code assessment test cases are retained as private grading configuration, but actual execution still requires a separate resource-limited sandbox service—the client never executes them. Chat thread-list pagination, moderation queues/appeals, block/mute, offline-send queues, reconnect gap recovery, and orphan-asset cleanup likewise remain service-backed launch work; message pagination/search and edit/delete/report client interactions are implemented.

The 4 MB browser flashcard store is a bounded offline convenience, not a multi-device institutional record. Large libraries, multi-device sync, backups, shared decks, and institution-managed retention require a principal-scoped server repository with pagination, revisions, encryption, and export/restore. Mobile/browser notification quotas also mean high-volume reminder delivery should use an institution push service rather than attempting one local notification per card.

Those should be treated as scoped product work, not implied by the generic JSON gateway. The recommended next milestone is an institution pilot contract plus security/accessibility testing, followed by the highest-priority standards integrations (typically OneRoster and LTI 1.3).
